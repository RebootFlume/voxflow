# 项目重构需求说明书：从 PyTorch 迁移至 Rust + ONNX Runtime / GGUF 双原生引擎

## 1. 项目背景与转型目标

目前项目已使用 Python + PyTorch 完成全部业务逻辑与功能开发（PoC 验证完成）。为提升桌面客户端的性能、启动速度、降低显存占用并彻底脱离庞大的 Python 环境（实现零 Python 依赖打包），现决定进行技术栈转型与底层引擎重构。

- **目标语言**：Rust（客户端主程序与业务逻辑）
- **目标交付物**：轻量化、高效率、秒级启动且具备高稳定性的桌面端应用
- **约束条件**：
  - **UI 界面完全不动**，当前界面已定稿，任何像素级改动都不允许
  - **Python 代码临时保留**，仅作为像素级迁移的对照凭证。迁移完成并整体验证通过后，统一移除全部 Python 代码和 Python 库
  - **最终目标：完全移除 Python 环境**（包括 Python 运行时、所有 pip 依赖、sidecar 进程），最终产物为纯 Rust 编译的原生二进制

---

## 2. 整体架构设计（双引擎架构）

为同时兼顾不同模态/架构模型（ASR、TTS、LLM）的性能与兼容性，放弃单一 PyTorch 运行时，改用**无 Python 依赖的 C/C++ 原生双引擎架构**：

```
                    +-----------------------------------+
                    |         Rust 业务主程序           |
                    +-----------------------------------+
                                      |
                      +---------------+---------------+
                      |                               |
                      v                               v
        +---------------------------+   +---------------------------+
        | ONNX Runtime (ort Crate)  |   |    llama.cpp (GGUF)       |
        +---------------------------+   +---------------------------+
        | 适用于:                   |   | 适用于:                   |
        | - TTS (语音合成)          |   | - LLM (大语言模型)        |
        | - 传统/小类型 ASR 模型    |   | - 具备 GGUF 适配的 ASR    |
        | - 图像及通用神经网络      |   | - 纯文本/多模态 Token 生成|
        +---------------------------+   +---------------------------+
```

### 引擎部署方式（推荐）

引擎**内嵌为 Tauri crate**，不走 IPC：

- Tauri 主程序直接调用 Rust 推理函数（零 IPC 序列化开销）
- 推理线程通过 `spawn_blocking` 或独立 tokio task 运行，不阻塞 UI
- 崩溃隔离：推理线程 panic 不影响 Tauri 主进程（catch_unwind + panic hook）

## 3. 模型格式与来源策略

**不在原始 PyTorch 仓库里折腾导出**，直接寻找已提供 ONNX/GGUF 格式的仓库：

### ASR 双路线（语音识别 · 输入法级秒出字）

| 模型 | 当前格式 | 目标格式 | 来源策略 |
|------|---------|---------|---------|
| 路线 | 格式 | 引擎 | 候选模型 | HuggingFace 仓库 | 特点 |
|------|------|------|---------|------------------|------|
| A: GGUF | `.gguf` | `llama-cpp-2` | Qwen3-ASR-0.6B | `ggml-org/Qwen3-ASR-0.6B-GGUF` | 社区量化丰富，显存可控 |
| A: GGUF | `.gguf` | `llama-cpp-2` | Qwen3-ASR-1.7B | `ggml-org/Qwen3-ASR-1.7B-GGUF` | 更高精度，需要更多显存 |
| B: ONNX | `.onnx` | `ort` | SenseVoice-Small | 待确认 | 原生 ONNX，零转换损耗 |
| B: ONNX | `.onnx` | `ort` | Paraformer | 待确认 | 毫秒级非自回归推理 |

**共同目标**：输入法级秒出字（非自回归并行解码，非逐 token 自回归生成）

**切换机制**：ASR 模块允许用户在 GGUF / ONNX 推理框架之间切换，切换后自动加载对应格式的模型。前端提供框架选择器（如 `GGUF (llama.cpp)` / `ONNX (ort)`），切换时触发模型重载。

### TTS 单路线（语音合成 · 开箱即用与自然度）

| 路线 | 格式 | 引擎 | 候选模型 | HuggingFace 仓库 | 特点 |
|------|------|------|---------|------------------|------|
| ONNX | `.onnx` | `ort` | Kokoro-82M | `onnx-community/Kokoro-82M-ONNX` | 82M 参数，轻量快速，多语种 |
| ONNX | `.onnx` | `ort` | VITS / MeloTTS / Piper | 各自仓库 | 生态成熟，社区维护活跃 |

**为什么 TTS 只走 ONNX**：GGUF 生态中几乎找不到成熟的 TTS 模型——语音合成的量化转换远比 LLM/ASR 复杂。ONNX 是唯一拥有大量现成离线语音包的格式。

**TTS 框架固定**：TTS 模块不提供推理框架选择器（只有 ONNX 一条路），避免用户困惑。如未来出现 GGUF 格式的 TTS 模型，再开放切换。

### 架构美感

```
              ┌─────────────────────────────┐
              │       Rust 业务主程序        │
              │    (Tauri + 模型管理器)       │
              └──────────┬──────────────────┘
                         │
            ┌────────────┴────────────┐
            │                         │
            ▼                         ▼
  ┌──────────────────┐    ┌──────────────────┐
  │  ort (ONNX)      │    │  llama-cpp-2     │
  │  ─ ASR 路线 B    │    │  ─ ASR 路线 A    │
  │  ─ TTS 主力      │    │                  │
  └──────────────────┘    └──────────────────┘
  SenseVoice/Paraformer   Qwen3-ASR GGUF
  Kokoro-82M ONNX
```

两个引擎各司其职，不互相绑架。用户在 ASR 设置页可切换框架，TTS 设置页无需选择。

### 来源优先级

1. **HuggingFace 预转换仓库**：搜索 `onnx` / `gguf` tag，优先选社区维护的量化版本
2. **本地已有模型直接复制**：已下载的 PyTorch 模型作为参考，评估是否可直接用于验证
3. **CapsWriter 方案复用**：CapsWriter 的 Qwen3-ASR GGUF 实现可作为参考（encoder + llama.cpp LLM 架构）
4. **手动转换**：作为最后手段，用 `optimum-cli` / `llama.cpp/convert.py` 自行转换

### 模型格式速查

| 模型 | 当前格式 | 目标格式 | 来源 |
|------|---------|---------|------|
| Qwen3-ASR-0.6B | PyTorch | **GGUF** | `ggml-org/Qwen3-ASR-0.6B-GGUF` |
| Qwen3-ASR-1.7B | PyTorch | **GGUF** | `ggml-org/Qwen3-ASR-1.7B-GGUF` |
| SenseVoice-Small | — | **ONNX** | 待确认 |
| Paraformer | — | **ONNX** | 待确认 |
| Kokoro-82M | PyTorch | **ONNX** | `onnx-community/Kokoro-82M-ONNX` |
| 未来 LLM | — | GGUF | 直接从 HuggingFace 下载 GGUF 量化版本 |

## 4. 技术执行路线与任务拆分

### Phase 0：模型导出验证（1-2 周，Python 侧，最高优先级）

**这是整个方案的前提条件。必须先做，做了再决定后续路径。**

1. **Qwen3-ASR GGUF 验证**：
   - 在 HuggingFace 搜索 `Qwen3-ASR` 相关的 GGUF 仓库
   - 评估 CapsWriter 的 GGUF 方案是否可直接复用
   - 验证 GGUF 版本的识别精度与 PyTorch 原版对比

2. **Kokoro TTS ONNX 验证**：
   - 搜索 HuggingFace 上 Kokoro 的 ONNX 版本
   - 如果没有，评估替代方案（LuxTTS、Chatterbox 等已有 ONNX 的引擎）

3. **输出精度对齐**：
   - 保存 PyTorch 原始输入输出 Tensor（`.npy` 矩阵）
   - 用 ONNX Runtime / llama.cpp 推理同一输入，对比输出差异
   - 精度要求：误差 $< 10^{-5}$（ASR 文字输出完全一致）

4. **决策点**：确认最终用哪个模型格式、哪个推理引擎

### Phase 1：Rust 基础设施搭建（与 Phase 0 并行）

1. **Tauri crate 结构搭建**：
   - 在 `src-tauri/` 下创建推理模块目录结构
   - 配置 `Cargo.toml` 依赖（ort、llama-cpp-2、cpal 等）

2. **推理引擎集成验证**：
   - `ort` crate 加载一个简单的 ONNX 模型，验证推理链路
   - `llama-cpp-2` crate 加载一个 GGUF 模型，验证推理链路

3. **音频采集 PoC**：
   - 用 `cpal` 实现麦克风采集，替代 Python `sounddevice`
   - 验证回调延迟、设备热插拔

4. **统一推理 Trait 设计**：
   ```rust
   trait InferenceEngine: Send + Sync {
       fn load_model(&mut self, path: &Path, device: &str) -> Result<()>;
       fn infer(&self, input: &InferInput) -> Result<InferOutput>;
       fn unload(&mut self) -> Result<()>;
       fn is_loaded(&self) -> bool;
   }
   ```

### Phase 2：逐模块翻译（Phase 0 完成后）

**关键原则：像素级平移，代码翻译，UI 不动。**

1. **音频处理模块**：
   - `numpy` → `ndarray` crate
   - `soundfile.read` → `symphonia` / `hound`
   - `sounddevice.InputStream` → `cpal`
   - 线性重采样 → `rubato`
   - 写对照测试确保输出一致

2. **ASR 引擎**：
   - `qwen_asr` → `ort`（ONNX）或 `llama.cpp`（GGUF）
   - 参考 CapsWriter 的 `qwen_asr_gguf/inference/` 实现
   - 流式推理接口设计（边识别边输出文字）

3. **TTS 引擎**：
   - `kokoro.KPipeline` → `ort`（ONNX）或寻找替代引擎
   - 保留 voice cloning 功能（需确认 ONNX 路径是否支持）

4. **模型管理**：
   - `huggingface_hub` → Rust `hf-hub` crate 或 `reqwest` 自研
   - 支持镜像源（`hf-mirror.com`）、断点续传、进度回调
   - 模型缓存目录与当前 Python 方案兼容（`AppData/.../models/`）

5. **每模块完成时写对照测试**：
   - Python 输出作为 ground truth
   - Rust 输出与 Python 输出逐字节对比

### Phase 3：集成与替换

1. **Rust 引擎接入 Tauri**：
   - 在 `src-tauri/` 中集成推理模块
   - 前端通过 `invoke` 调用 Rust 推理命令
   - **UI 完全不动**，只替换底层调用

2. **逐模块替换**：
   - 每个 Python 模块迁移完成并用对照测试验证通过
   - 前端通过 `invoke` 调用 Rust 推理命令
   - **UI 完全不动**，只替换底层调用
   - **Python 代码在迁移期间全部保留**，不提前删除

3. **整体迁移完成 + 全量回归后，统一移除 Python**：
   - 所有模块迁移完成，对照测试全部通过
   - 端到端回归测试：完整功能流程验证
   - 移除 Python sidecar 进程、`python-backend/` 目录、所有 Python 依赖
   - Tauri 打包不再包含 Python 运行时
   - 最终产物为纯 Rust 原生二进制

4. **最终产物对比**：
   - 打包体积：当前（~500MB+ Python）→ 目标（<50MB 纯 Rust）
   - 安装方式：当前（需 Python 环境）→ 目标（双击即用）

## 5. 性能基准定义

重构的目的是提升性能，必须定义明确的达标指标：

| 指标 | 当前 PyTorch | 目标 | 测试方法 |
|------|-------------|------|----------|
| 模型加载时间 | ~39s | <5s | 冷启动计时（含 import） |
| 单次推理延迟（1s 音频） | ~2s | <0.5s | 10 次取平均 |
| 显存占用（单模型） | ~2GB | <1GB | nvidia-smi |
| 内存占用 | ~3GB | <1GB | 任务管理器 |
| 启动到可用 | ~40s | <5s | 端到端计时 |
| ASR 识别准确率 | 基准 | ≥基准 | 相同音频对比文字输出 |
| TTS 音质 | 基准 | ≥基准 | MOS 主观评分 |

## 6. 音频处理移植对照表

| Python 操作 | Rust 等价库 | 备注 |
|------------|------------|------|
| `sounddevice.InputStream` | `cpal` | 跨平台音频 I/O，需处理设备热插拔 |
| `soundfile.read()` | `symphonia` | 支持 WAV/MP3/FLAC/OGG |
| `numpy` 数组操作 | `ndarray` | 大部分 API 有对应 |
| 线性重采样 (`np.interp`) | `rubato` | 高质量重采样 |
| `float32 ↔ int16` 转换 | 直接操作 `ndarray` | 零拷贝 |
| FFmpeg 解码（兜底） | `ffmpeg` 命令行调用 | 保持当前方案 |
| `base64` 编解码 | `base64` crate | 标准库 |

## 7. 流式推理接口设计

Rust 重写时**一开始就设计流式接口**，不走先批量后改流式的弯路：

```rust
trait AsrEngine: InferenceEngine {
    /// 流式识别：每收到一个音频 chunk，返回部分识别结果
    fn recognize_stream(&self, chunk: &[f32], is_final: bool) -> StreamResult;
}

struct StreamResult {
    text: String,           // 本次返回的文字
    is_final: bool,         // 是否为最终结果
    timestamps: Vec<f64>,   // 时间戳（可选）
}
```

流式模式的好处：
- 用户体验好（边说边显示）
- 内存占用低（不需要一次性加载整段音频）
- 与 CapsWriter 的分片架构兼容

## 8. 失败回退策略

| 风险 | 回退方案 |
|------|---------|
| ONNX 导出精度不达标 | 降级到 GGUF 方案；或保留 PyTorch 作为 fallback |
| GGUF 量化后 ASR 识别率下降 | 优先用 F16 量化（不压缩），或寻找更优的量化方案 |
| Kokoro 无 ONNX 路径 | 替换为其他有 ONNX 支持的 TTS 引擎（LuxTTS、Chatterbox） |
| Rust 引擎不稳定 | 迁移期间继续保留 Python 侧作为对照，定位问题后修复 Rust 实现；整体验证通过后再统一移除 |
| 特定硬件不兼容 | ONNX Runtime 支持 CPU/CUDA/DirectML/Metal，覆盖面广 |

## 9. 关键避坑与质量要求

1. **绝对禁止崩溃（Panic Free）**：严禁使用容易引发 FFI 崩溃的绑定，捕获所有模型加载与推理异常，确保软件稳定运行。
2. **内存零拷贝（mmap）**：确保 ONNX 及 GGUF 加载时启用内存映射（Memory Mapping），实现秒级启动。
3. **分阶段对齐**：重构过程中保留 Python 对照环境，逐层对齐特征提取与模型输出 Tensor，确保重构后效果无损。
4. **RAII 显存管理**：Rust 的 Drop trait 天然保证模型卸载时显存/内存 100% 回收，不依赖 GC。
5. **UI 完全不动**：前端代码零改动，所有变更都在 `src-tauri/` 和推理模块内。
6. **Python 迁移期间保留**：迁移期间 Python 代码和所有 pip 依赖全部保留作为对照凭证。整体迁移完成并全量回归验证通过后，统一移除全部 Python 相关内容。最终产物为纯 Rust 原生二进制，不包含任何 Python 环境。

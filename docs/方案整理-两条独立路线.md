# 两条独立技术路线方案（整理版）

## 核心决策：放弃中间件，直接原生 C 库 + 独立架构

```text
┌─────────────────────────────────────────────────────────────────────────┐
│  桌面应用层（voxflow / Tauri / Frontend）                                │
│  ├── 不直接依赖任何推理引擎                                           │
│  ├── 通过 IPC（Tauri invoke / sidecar 事件）与推理框架通信              │
│  └── 崩溃隔离：推理引擎崩了，桌面应用继续运行                           │
└──────────────────────┬────────────────────────────────────────────────────┘
                       │ Tauri invoke / Queue / Socket
                       ▼
┌─────────────────────────────────────────────────────────────────────────┐
│  推理框架层（独立进程 / 独立服务）                                      │
│                                                                         │
│  路线 A：原生 llama-cpp（GGUF / ASR LLM）                               │
│  ├── 官方编译：llama.dll / libllama.so                                │
│  ├── Rust 侧：自写 FFI 绑定（ctypes 风格，不依赖 llama-cpp-2 crate）     │
│  ├── 模型：Qwen3-ASR-0.6B GGUF                                        │
│  └── 特性：多模态 audio embedding 注入 + text generation             │
│                                                                         │
│  路线 B：原生 sherpa-onnx（ONNX / ASR 流式）                             │
│  ├── 官方下载：sherpa-onnx .so / .dll + 模型文件                       │
│  ├── Rust 侧：直接调用 C API（不依赖 sherpa-onnx Rust crate）           │
│  ├── 模型：Qwen3-ASR ONNX encoder + LLM（或 sherpa-onnx 内置支持）     │
│  └── 特性：流式识别、热词、时间戳                                       │
│                                                                         │
│  A 和 B 完全独立：各有自己的进程 / 服务 / 端口 / 状态                 │
└─────────────────────────────────────────────────────────────────────────┘
                       │
                       ▼
         崩溃互不影响（一个挂了，另一个继续工作，桌面应用正常）
```

---

## 为什么放弃中间件（Crate 层）

### 已尝试/已确认的问题

| 中间件 | 问题 |
|--------|------|
| `llama-cpp-2` (Rust crate v0.1) | 编译通过但无实际实现；API 不完整（缺少 multimodal embedding 注入）；与 Qwen3-ASR 的音频 token 处理不匹配 |
| `sherpa-onnx` (Rust crate) | 依赖链复杂，与 Tauri / Windows DLL 加载有冲突；版本不稳定 |

### 直接原生的优势

| 对比项 | 中间件（Crate） | 原生 C 库（直接 FFI） |
|--------|----------------|----------------------|
| 编译控制 | 依赖 crate 版本，无法干预 C 编译选项 | 自己控制 CMake / 编译参数（如 CUDA 层数、multimodal 开关） |
| API 完整性 | 只暴露 crate 封装的部分 | 完整访问官方 C API（包括内部 embedding 注入、流式控制） |
| 崩溃隔离 | crate 在 Rust 进程内，崩溃带走整个应用 | 独立进程 / 独立服务，桌面应用不受影响 |
| 调试难度 | crate 抽象层增加调试难度 | 直接看官方文档和 C 代码 |

## 两条路线的详细定义

### 路线 A：原生 llama-cpp（ASR / LLM）

```
来源：llama.cpp 官方仓库 / 发行版
文件：
  - llama.dll（Windows） / libllama.so（Linux） / libllama.dylib（macOS）
  - ggml.dll / libggml.so（底层张量库，通常随 llama.dll 打包）
  - Qwen3-ASR-0.6B-Q8_0.gguf（模型文件，从 ggml-org/Qwen3-ASR-0.6B-GGUF 下载）

集成方式：
  Rust 代码不 import llama-cpp-2 crate
  而是：
    1. 自己写 FFI 绑定（参考 CapsWriter-Offline 的 llama.py 做法）
       - 绑定 llama_model_load_from_file
       - 绑定 llama_init_from_model
       - 绑定 llama_batch_init / llama_batch_set_embd / llama_decode
       - 绑定 llama_tokenize / llama_token_to_piece
    2. 加载模型：直接调用 C API，不经过任何 Rust 封装层
    3. 推理：手动构造 batch（包含 audio embedding 注入）

关键技术参考：
  CapsWriter-Offline 的 core/server/engines/force_aligner_gguf/inference/
  - llama.py（ctypes 绑定）
  - asr.py（_build_prompt_embd 构造多模态 embedding，_decode 执行推理）
  - encoder.py（ONNX audio encoder 提取 mel + embedding）
```

### 路线 B：原生 sherpa-onnx（ASR 流式）

```
来源：k2-fsa/sherpa-onnx 官方发行版
文件：
  - sherpa-onnx-core.so / .dll
  - sherpa-onnx-ffmpeg.so / .dll（可选，音频解码）
  - Qwen3-TTS / ASR 模型文件（ONNX 格式，sherpa-onnx 内置支持）

集成方式：
  Rust 代码不 import sherpa-onnx crate
  而是：
    1. 直接调用 sherpa-onnx C API（sherpa-onnx 提供 .h 头文件）
    2. 或通过 subprocess 调用 sherpa-onnx 预编译的命令行工具
    3. 流式识别：sherpa-onnx 的 StreamingRecognizer 接口

优势：
  - sherpa-onnx 已内置 Qwen3-ASR 的完整推理流程（不需要自己构造 embedding）
  - 流式、热词、时间戳功能成熟
  - 部署简单：一个 .so + 模型文件
```

## 独立架构要求（崩溃互不影响）

```
桌面应用（Tauri + React）
│
├─ 不直接 link 任何推理引擎的 .so / .dll
│
├─ 通过 IPC 调用推理服务（两种方式可选）：
│   方式 1：Tauri invoke → Rust 主进程 → 通过 queue / socket 调用子服务
│   方式 2：直接 WebSocket / TCP → 独立服务进程（类似 CapsWriter 的 ProcessManager）
│
└─ 如果推理服务崩溃：
    → 桌面应用收到错误响应（而非直接 crash）
    → 桌面应用继续运行，可重新启动推理服务

推理服务（独立进程 / 服务）
│
├─ 路线 A 服务：llama.cpp 加载 → 监听端口 / 队列 → 执行推理 → 返回结果
│   → 如果 GGUF 加载失败：服务返回错误，不影响桌面
│   → 如果推理过程中内存溢出 / SIGSEGV：服务进程退出，桌面应用通过超时检测到
│
├─ 路线 B 服务：sherpa-onnx 加载 → 监听 → 流式识别 → 返回结果
│   → 同上，独立崩溃，不影响桌面
│
└─ 服务之间：A 和 B 完全独立，各自有自己的进程、端口、状态文件
```

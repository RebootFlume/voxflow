# 推理引擎架构重构方案（ASR + TTS 统一）

> 状态：待评审（未动代码）
> 范围：`src-tauri/src/inference/`、`src-tauri/src/tts/`、`model_manager.rs`、前端模型加载链路
> 目标：框架（引擎）与模型（数据）解耦，加框架/加模型只写自己的配置，与存量零耦合

## 0. 结论摘要

| 问题 | 结论 |
|---|---|
| ASR 现成方案是什么 | ASR 已有「引擎 trait + 注册表 + 按格式路由 + 前端不猜框架」的完整框架轴，是 TTS 的范本；但模型轴仍是硬编码（引擎内部有模型名分支） |
| 改动影响大么 | 行为不变是重构的硬约束：事件协议、下载/清单、前端 ASR 路径、打包产物都不变。会动的是 Rust 内部结构与命令签名，前端 TTS 页有一轮联动修改 |
| 改动量大么 | 中等。TTS 侧为主（约 6 文件重构 + 4 文件删除 + 2 新文件）；ASR 侧很小（约 40 行硬编码收敛进数据）；共享脚手架抽取约 1 新文件 |

## 1. 背景与目标

当前问题：
1. TTS 侧 `TtsService` 是大 if/else 分发器（字符串嗅探 `is_e2e` 决定后端），违反项目自定的 AGENT.md 规则 11。
2. 同一个 8 模型清单存在三处（`model_manager.rs` REGISTRY / `e2e_registry.rs` 枚举 / `sherpa.rs` 的 cli_args+required_files），靠人肉同步。
3. ASR 侧骨架已达标，但 `llama_server.rs`、`sherpa_asr.rs` 内部仍有模型名硬编码分支。
4. 存在三个推理抽象（`InferenceEngine` / `AsrEngine` / `TtsEngine`），`InferenceEngine` 只剩 llama_server 一个陈旧 impl，未走 registry 路径。
5. 已知功能性 bug（device 失效、UI 冻结、Supertonic 语言不可选、Pocket 克隆 no-op、24000 采样率硬编码）大多由结构问题引发，重构后自然消失。

目标：
- 框架轴（引擎实现）与模型轴（描述符数据）正交，只在 `ModelSpec` 契约上汇合。
- 加模型 = 加一条数据；加框架 = 实现 trait + 注册一行。
- ASR / TTS 同构，共享 Device、进程 supervisor、注册表脚手架。
- 为 PyTorch 引擎（ASR + TTS）预留零侵入接入点。

## 2. 现状盘点

### 2.1 ASR 现有架构（已达标部分，作为范本）

```
commands (rust_load_asr / rust_get_status / rust_unload_asr)
    → inference/registry.rs: AsrRegistry（互斥 + 按 format 路由 + 显存估算）
        ├─ ("gguf",  LlamaAsrAdapter)   → llama_server.rs 子进程 + HTTP
        └─ ("onnx",  SherpaAsrEngine)   → sherpa_asr.rs websocket server 常驻
    → tts/spec.rs: ModelSpec SPECS（下载/展示/引擎参数/能力，单一真源）　【已落地，见 §0.1】
```

已具备的机制：
- `AsrEngine` trait（`inference/engine.rs`）：`framework()` + `load_model_with_device`（默认转发）+ `load_model_with_stage_and_device` + `unload` / `is_loaded` / `current_model` / `transcribe` / `vram_estimate_mb`（默认 None）。**全部带默认实现，向下兼容**。

## 3. 目标架构

### 3.1 核心原则：两个轴 + 一条契约

```
框架轴（代码，少而稳定）          模型轴（数据，多而增长）
TtsEngine trait 实现               ModelSpec 描述符
  ├─ SherpaTtsEngine  ───────────────┼── sherpa 模型: kokoro-v1_1 / matcha / ...
  ├─ PyTorchTtsEngine（未来）────────┼── pytorch 模型: qwen3-tts / ...
  └─ AsrEngine 实现（已有）──────────┼── asr 模型: qwen3-asr-0.6b / sensevoice / ...
              ↑ 解释描述符（通用代码，无模型名分支）↓
                    └── 契约：ModelSpec ──┘
```

- 引擎是描述符的通用解释器，禁止 `if model == "kokoro"` 这类分支。
- 加模型 = 加数据；加框架 = 实现 trait + 注册一行。
- ASR / TTS 共用同一张 `ModelSpec` 表（domain 字段区分），共享 Device / 进程 supervisor / 注册表骨架。

### 3.2 三层模型：接口 / 协议 / 实例

```
顶层接口   TtsEngine / AsrEngine trait（行为抽象）   "能做什么"   load / synthesize / transcribe
          ↑ 动词，代码，几乎不变
数据协议   ModelSpec schema（领域协议）             "用什么字段描述一个模型"  id / languages / voice_mode / backend
          ↑ 名词，迁移时冻结的契约
数据实例   每条模型的描述符                         "具体答案"   kokoro: Preset{103} · zipvoice: Clone{...}
          ↑ 自由变动，互不影响
```

- **接口层**只承诺"给我一份 spec，我照着干活"，不承诺任何模型细节。
- **接口签名冻结**：`TtsEngine` / `AsrEngine` 全部方法统一 `&self` + 内部锁（可变状态收进 `Mutex`/`RwLock`），registry 才能安全持有 `Arc<dyn TtsEngine>`。`TtsService` 现有 `&mut self` 语义在 P1 改造（见 4.2 traits.rs 行）。
- **协议层**是"能力的声明格式"（字段与枚举），迁移时冻结；此后加模型 = 照协议填表，不动协议。
- **实例层**每模型一条，增改只碰自己的记录，其他模型零影响。
- 未来唯一可能发生的共享改动是"协议升级"（出现 schema 表达不了的新能力）——一次评审过的独立扩展，不是加模型的常规动作。

### 3.3 依赖方向（单向，无环）

```
commands (IPC, async)  →  Registry (路由+互斥)  →  Engine (框架)  →  ModelSpec (数据)
                              ↑                        │
                    model_manager (下载/清单/删除)  ←───┘ 读描述符
```

### 3.4 目标文件布局

```
src-tauri/src/inference/
├── device.rs          # 共享：Device 枚举 + 进程 supervisor（从 llama_server 抽出）
├── slot.rs            # 共享：泛型 EngineSlot<T>（互斥 + 路由骨架）
├── registry.rs        # AsrRegistry（已有，套 slot，行为不变）
```

#### voice_mode 契约（迁移时冻结，驱动 UI 与引擎）

```rust
enum VoiceMode {
    /// 无音色选择（单音色）——Matcha / Kitten
    Fixed,
    /// 预设音色（sid 制）——Kokoro 系 / Supertonic
    Preset {

        overrides_preset: bool,        // 克隆激活时忽略 sid（当前克隆模型都是）
    },
    /// 预设 + 克隆并存——当前无此模型，schema 预留，未来模型无需扩协议

}
```

### 4.6 PyTorch 双域接入方式（扩展性验收）

PyTorch 扩展**同时覆盖 ASR 与 TTS，两个域独立接入、互不依赖**：

- **ASR 域**：`inference/pytorch.rs` 实现 `AsrEngine`（子进程 + HTTP，复用 supervisor）→ `AsrRegistry` 注册一行。
- **TTS 域**：`tts/engines/pytorch.rs` 实现 `TtsEngine`（同模式）→ `TtsRegistry` 注册一行。
- 模型侧：各自的 `ModelSpec.backend` 加 `PyTorch { model_key, ... }` 段，每模型一条数据。
- 两个引擎实现互不知道对方存在；命令层、前端、API server、显存监控全部经由各自 registry，零改动。
- 接入顺序可独立：先 ASR 后 TTS，或反之；任一域先接入即可验证"零 if/else 扩展"是否成立（见 P5）。

### 4.6.1 PyTorch 运行环境与模型获取（归属决策）

**归属规则：按来源分**（不是按框架分）

| 来源 | 归属 | 现状 |
|---|---|---|
| GitHub release 资产（10 个模型 + 4 个运行时包 + vocoder） | Rust `net` | ✅ 已收敛为唯一实现 |
| HuggingFace（GGUF 2 行，未来 PyTorch 模型） | Python 侧 `huggingface_hub` | ⏳ PyTorch 轮迁移 |

依据（实测对比）：HF 官方库在**断点续传**（`.incomplete` + Range，"总是续传"，`resume_download` 已废弃）、**原子写**（`.incomplete` → rename）、`local_dir` 增量元数据、缓存复用（`HF_HOME`）、`HF_HUB_OFFLINE`、与 transformers 布局同源上全面优于 `hf-hub`；后者 Xet 与 5 次重试已具备，但**无 partial 落盘**、直接写目标路径、`local_dir` 不复用缓存。

**Python 从哪来**：把「Python 基础运行时」（embeddable + `huggingface_hub`/`hf_xet`，约 60MB，**不含 torch**）做成独立 zip 资产、走现有 `RuntimePkg` 流水线（marker / 校验 / 试启动），与 torch 依赖层分离。这样 ASR 用户下载 HF 模型只需一次性 60MB，而不是 3GB torch 环境。

**迁移清单（HF → Python 时）**
- spec 数据不变：`DownloadSource::HuggingFace(repo)` 保留；
- 删除 Rust 侧 `build_client_sync` / `IpcProgress` / `hf_hub` 依赖（`Cargo.toml`）；
- 契约保持：Python 进度回调 → Rust 翻译为同一族 `model_download_*` 事件；`local_dir = model_root/<spec.id>` 由 Rust 传参（单一真源）；下完仍由 Rust 用框架描述符判 `is_complete`；
- Python 侧待落实：**取消**（`snapshot_download` 无 cancel 参数 → 在进度回调里抛异常中止）、**token/proxy 注入**（`HF_TOKEN` / `HTTP(S)_PROXY` / `HF_HOME`，Rust `CONFIG` 仍为单一配置源）。

**数据模型缺口（PyTorch 前需补）**：`FilePolicy` 对分片权重需要 `IndexOf` 变体（`model.safetensors.index.json` 才是"主文件"，`Largest` 会挑错最大分片）。

### 4.7 原生 C-API + stdio worker（第二期可选项，不进入当前重构）

参考 CapsWriter 模式（C-API 进 worker + 管道通信，生产已验证）。当前**不实施**，列为第二期独立工程；当前架构重构不依赖它。

形态：
```
主进程（只做 IPC，HTTP 或 stdio 客户端）
   │ stdio 管道（帧协议）
   ▼
原生 worker 子进程（一个通用 worker 二进制 + 插件式加载）
   ├─ llama.dll（C API，~20 函数绑定，流式/注入能力）
   └─ sherpa-onnx.dll（C API）
```

要点：
- **worker 内部**绑 C-API（直接函数调用，零网络栈）；**主进程 ↔ worker** 走 stdio 管道（帧协议：长度前缀 / JSON-lines）。
- 与 HTTP 引擎（llama-server / pytorch worker）**并存于 registry**，不替换、不冲突；传输方式是引擎内部细节。
- 共享一个 supervisor（spawn / 就绪 / 崩溃 / kill），与 HTTP 形态复用同一套进程生命周期管理。
- 触发条件（满足其一才立项）：流式 ASR（逐 token 输出）、llama-server 给不了的 embedding 注入、常驻免冷启。
- 契约影响：该引擎内部 `ArgSpec`（CLI argv）替换为 worker 请求协议（C-API 参数结构体），见 7.6 适用范围注；架构主体不动。
- 代价（诚实清单）：自维护绑定 + ABI 锁版本、替换已验证实现的重新验证（启动/就绪/崩溃/卸载/显存/benchmark）、sherpa C-API 文档比 llama 薄、跨模型逐一冒烟。

#### 4.7.1 立项依据：端口维护面实测（2026-09-19 核对）

**动机澄清（防立项理由漂移）**：本条的真实收益是「**消端口维护面**」与「**常驻免冷启**」，**与黑窗口无关**——控制台窗口已由 `process_hidden::hide_console_window` 覆盖全部 spawn（窗口事件探针实测零控制台窗口），"闪黑框"是前端加载遮罩问题（已修）。另注意：`4.7` 的 worker 形态**仍有子进程**（主进程 + worker），因此走这条路**不会**顺带消灭窗口/端口类问题，worker 是新 spawn，须同样隐藏窗口。

**当前端口清单**（实测 `src-tauri/src`）：

| 服务 | 端口 | 传输形态 | 附带的维护面 |
|---|---|---|---|
| llama-server（ASR GGUF） | `8931`（可漂移） | HTTP | `kill_port_owner` + `find_free_port(port+1)` + `wait_port_closed` + health 轮询 + `/props` 读运行中模型/温度 + `current_port()` **会话内端口延续**（`llama_server.rs` 53 处 port 引用） |
| sherpa ASR | `9002` | websocket `ws://127.0.0.1:{port}/asr` | 加载前 `kill_port_owner(9002)` + `wait_port_closed(3s)` |
| api_server（对外 OpenAI 兼容） | 用户配置 | HTTP | **必须保留**：产品接口，非内部传输 |
| TTS | **无** | CLI 子进程 + 临时 WAV | **0**（`tts/` 下 grep `port` 命中全为误报：`export_dir` / `supports_clone`） |

**分域收益**：

| 域 | 切 C-API 能否减少端口维护 | 说明 |
|---|---|---|
| TTS | ❌ | 本来 0 端口，此项收益为零 |
| ASR | ✅ | 可消掉 8931 / 9002 及上表全部端口状态机 |
| api_server | ❌ | 对外协议，永远保留 |

**代价（补充）**：
- worker 形态下端口消掉但**不归零**：换成 stdio 帧协议 + 进程生命周期管理（spawn/就绪/崩溃/kill 仍需 supervisor）。
- 端口守卫的清理面**已收敛但仍非零**（本轮核对修正）：`kill_port_owner` 并非"杀任意占口进程"，而是先做归属判定 `is_our_engine_exe`（`device.rs:48-52`，要求 exe 路径位于本软件 `libs/` 下），非自有进程**保守跳过不杀**（`device.rs:105-108` 打日志走换端口/报错）。残留风险：同机**另一个 VoxFlow 实例**的引擎也在 `libs/` 下 → 会被清理。消端口即消掉这条（已收窄的）风险。

**推论（约束）**：
- 决策 #4「TTS 常驻」若立项，形态**必须**选 stdio / C-API，**禁止**做成 HTTP server——否则新增第 3 个端口 + 配套端口守卫风险，常驻收益被端口维护面抵掉。
- 新增 spawn（worker）沿既有约束：必须 `hide_console_window`，否则黑窗口以新形态回归。
- ASR 域改 C-API 的收益（消端口）**远大于** TTS 域；TTS 域立项的唯一理由是"常驻免冷启"（见 7.4）。
- 本仓库 `sherpa-onnx` 运行时包**已含** `lib/sherpa-onnx-c-api.dll` + `.lib` + `include/sherpa-onnx/c-api/c-api.h` → 立项无需改下载源，只需在 `SHERPA_CUDA_AUX_FILES` 追加校验项 `lib/sherpa-onnx-c-api.dll`。

## 7. 风险与对策（需重点考虑的问题）

### 7.1 CLI 参数迁移回归（最高风险）
风险：`cli_args` 从 8 个 match 分支迁到描述符数据，flag 拼错/漏配 → 合成失败或静默坏参数。
对策：**三层测试，明确自动化边界**：
- **(a) CI 自动化（契约层，无需真实模型/exe）**：
  - spec schema 校验测试：id 唯一、归一化唯一、required_files 非空、静态 flag 无空值、动态占位符格式合法。
  - **argv 黄金比对测试**：每个模型「描述符 + 运行时状态 → argv」与迁移前 `cli_args` 输出逐项 diff（黄金文件）。
  - 路由/互斥契约测试：假描述符 + mock 引擎，验证 registry 路由、互斥、active 查询。
- **(b) 本机手工冒烟（真实模型 + sherpa exe，不进 CI）**：8 模型逐一加载/合成，写成可执行脚本清单（沿用 inference/tests.rs 现有用例 + tests/tts_models_smoke.rs 数据驱动矩阵 + tests/e2e_tts.rs（均 #[ignore]）），由开发者在有模型环境的机器上跑。**验收标准中的"冒烟"一律指本层，非自动化**。
- **(c) 端到端 UI 走查**：加载/合成/切语言/切模型/克隆全流程。

### 7.2 三处清单合并的语义差异
风险：model_manager 用展示名（Kokoro-v1_0），e2e_registry 用引擎 id/目录（kokoro-multi-lang-v1_0），合并后解析路径不一致。
对策：spec 查找接受展示名 / 引擎 id / 目录名三种别名，归一化匹配（见 4.2「模型名 → spec 查找契约」）；**前端保持传展示名不变**；复用现有 `resolve_download_dir` / `resolve_sherpa_model_dir` 的归一化逻辑（model_manager.rs:989-1021），删除 e2e_registry 后这两处改用 spec 表。schema 校验测试保证归一化唯一性（不允许两个条目归一化后相同）。

### 7.3 引擎态 vs 模型态边界（克隆参数归属）
风险：语音克隆参数（reference_audio/text）现在存于 SherpaTtsEngine 内部，registry 化后归属不清。
决策建议：克隆参数是「当前加载模型的运行时参数」，仍由引擎持有，registry 只路由不感知。`rust_set_tts_clone_voice` 的 `as_mut_sherpa()` 改为 registry 向下转型或引擎 trait 加可选方法（默认返回错误）。

### 7.4 sherpa TTS 常驻进程（范围控制）
风险：现在每次合成冷启子进程（每次重载 310MB 模型）。若在重构中顺手改成常驻，会引入进程生命周期/就绪握手/端口管理的新风险面。
决策建议：**本次重构不做**，列为独立优化项（引擎内部实现细节，接口不变，未来随时可做）。

### 7.5 删除 ort 依赖的连锁
风险：`ort` 2.0-rc.13 + DirectML 是重依赖，删通用 ONNX 线后可移除，但需确认无其他消费者（已查：全库仅 tts/service.rs + onnx.rs 使用）。移除后 Cargo.lock 变化大，需全量编译验证。
注意：这同时意味着「进程内 ONNX TTS」能力从代码库消失，未来若需要，以新引擎实现 + 重新加依赖的方式回归（符合架构）。

### 7.6 条件/动态参数：ArgSpec 类型化契约（冻结）
风险：Kokoro 的多词典（lexicon-us-en/gb-en/zh）、rule-fst（date/phone/number-zh）、Supertonic 的 --lang、ZipVoice 的克隆 flag 都是「有条件/运行时填充」参数。描述符若只支持静态映射，会丢失这些行为。
对策：描述符的 CLI 段用**类型化枚举**表达，解释器 `build_argv` 遍历 `Vec<ArgSpec>` 拼 argv，无模型分支：

```rust
enum ArgSpec {
    Static(&'static str, &'static str),            // "--num-threads" → "4"（恒定）
    File(&'static str, &'static str),              // "--kokoro-model" → "model.onnx"（必填，缺失报错）
    OptionalFile(&'static str, &'static str),      // 文件存在才加（单文件）
    JoinableFiles(&'static str, &'static [&'static str], char),
                                                   // 多候选按声明顺序 join 成一个 flag，存在才加入
                                                   // （--kokoro-lexicon=a,b,c；--tts-rule-fsts=d,e）
    RuntimeVar(&'static str, RuntimeKey),          // sid / lang / provider / num_threads / 克隆参数 / output
}
```

- 覆盖三类语义：必填文件、可选文件（含多候选 join）、运行时占位（sid/lang/克隆/output）。
- golden argv 测试对每个模型逐项比对，顺序按描述符声明稳定。
- 新增风险：JoinableFiles 的 join 顺序必须按描述符声明顺序，不允许排序——schema 校验测试锁死。
- schema 校验必须覆盖全部变体（必填 flag 无空值、可选文件路径非空、RuntimeKey 合法）。

> 适用范围：ArgSpec 契约服务于 **CLI 调用形态**（sherpa-onnx-offline-tts.exe / llama-server 参数）。若某原生引擎第二期切换为 C-API + stdio worker（见 4.7），该引擎内部的 `ArgSpec` 替换为 **worker 请求协议**（C-API 参数结构体 + stdio 帧格式），架构主体（registry / ModelSpec / trait）不受影响——这是引擎内部实现的替换，不是协议升级。

### 7.7 行为不变性验证成本
风险：纯重构最容易在「看起来等价、实则行为漂移」处埋雷（如事件 payload、错误文案、加载幂等判定）。
对策：迁移阶段每个子步独立提交、独立验证；关键行为（加载幂等、卸载、切模型互斥、API 并发 503）写契约测试（`cargo test --lib`）；最终验收跑自动化契约测试 + 本机冒烟矩阵（`cargo test --test tts_models_smoke -- --ignored --nocapture`）+ 手动 UI 走查。

### 7.8 ASR 收敛的风险低但需防误伤
风险：llama_server 的 `for_model`/`pick_mmproj` 与端口守卫耦合在同一文件，抽 supervisor 时可能误改启动参数（注释明示"参数已通过 benchmarks 验证，勿随意调整"）。
对策：supervisor 抽取为纯搬运（不改行为），llama 启动参数原样保留；benchmarks/ 下的验证脚本作为回归依据。

| 2 | **加载前置门禁**：缺框架时不进入 loading、不 spawn 进程，直接给可读原因（`modelLoader.runtimeGate`）。实测对照：修复前 `⏳启动引擎中 → ❌sherpa server 未找到`；修复后 `❌缺少推理框架（sherpa-onnx），已停止加载…` |
| 3 | **模型卡片内联失败原因**：状态文案不再要求 `isSelected && isLoaded`（旧条件导致失败时整段不渲染），并展示 `engines[kind].error` 原文；卡片同时标注「需先安装 X 框架」 |
| 4 | **启动 Splash 失败解释**：不再静默淡出，就地显示原因 + 「去框架页」/「先进入应用」 |
| 5 | **状态域对齐**：`applyEngineStatus` 镜像写 `asr.modelStatus`/`ttsModelStatus`（两套状态域并存曾导致徽章停在 loading）；超时文案 120s → 实际 20s |

### 10.3 本轮发现的既有缺陷（非本次引入，待单独处理）

1. **tokio panic（既有，已修复）**：启动后 `thread 'tokio-rt-worker' panicked: Cannot drop a runtime in a context where blocking is not allowed`。
   **根因（完整栈定位）**：`reqwest::blocking::Client` 构造时会自建 tokio Runtime，而 tokio 禁止在异步上下文中析构 Runtime。链为
   `rust_load_asr`（async 命令体，第 642 行）→ `registry()`（ASR 注册表**首次**初始化）→ `LlamaAsrAdapter::new` → `global_engine` → `LlamaServerEngine::new` → `with_config` → `Client::build()`。
   因只在"首次初始化"发生，属**竞态**：若被同步路径先初始化则无事，被 async/spawn_blocking 抢到则 panic（基线 stash 后复现一致）。
   **影响**：panic 点（642 行）早于 `model_loading` 事件（647 行）→ 前端乐观 loading 收不到任何终态 → **界面停在「加载中」直到 20s 超时对账**；另有 `get_vram_status` 路径 panic → 显存面板静默返回空值。
   **修复（已落地）**：在 `tauri::Builder::setup`（主线程、非异步）预热单例 `registry()`，把首次初始化固定在非异步上下文。
   **注意**：仅改「创建时机」，HTTP 调用的执行线程不变（仍在后台 `std::thread` / `spawn_blocking`），无新增主线程阻塞。
   **验证**：连续 3 次启动零 panic；ASR 三次加载成功（10.3s / 10.3s / 10.3s）；lib 测试 67 通过。
2. **手动放置的运行时其实已被识别**：本机 `target/debug/libs`（03:29 手动放置）为完整官方布局 `sherpa-onnx/{bin,include,lib}`，应用一直能正常加载；此前"都需要下载"的观感来自**框架页状态判定**与布局/校验口径，而非加载能力——已由 10.1 统一与 10.2 的入口修复覆盖。

## 11. 执行上下文契约（IPC 命令线程模型）

### 11.1 两类缺陷同源
- **缺陷 A（已修）**：async 上下文里创建/析构 `reqwest::blocking::Client` → tokio panic（见 10.3.1）。
- **缺陷 B（待修）**：同步命令**内联在主线程**执行 → 主线程被阻塞 I/O 占死，UI 冻结。
两者根因相同：**"代码在哪个执行上下文里跑"从未被定义为一条约束**。零散打补丁必然复发，需按契约统一整改。

### 11.2 实测证据（本机，WebView2 CDP 挂载 + 运行期探针）
方法：`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222` 启动应用，CDP 挂载页面后
`import('/src/lib/tauri.ts')` 调命令；先测空闲基线，再 fire 一个慢命令（不 await），期间连续探测廉价命令
`rust_get_data_root_info` 的往返延迟（任何 invoke 都必须经主线程投递）。

| 场景 | 命令本体耗时 | 运行期间探测 RTT |
|---|---|---|
| 空闲基线 | — | 7 / 7 / 6 ms |
| 慢**同步**命令 `rust_stop_llama_server` | 2100 ms | 7, **2096**, 9, 8 ms |
| 慢**异步**命令 `get_vram_status` | 1016 ms | 8 / 7 / 7 / 7 ms |

**结论**：同步命令内联执行，期间主线程消息泵停摆（窗口拖动/点击/IPC/托盘全停，Windows 标"未响应"）；
异步命令投递到 tokio，主线程不受影响。源码侧一致：tauri 2.11 `ResponseTag::block` 直接 `resolver.respond`
（在 IPC 处理线程内联，WebView2 下即主线程），`async_kind` 走 `async_runtime::spawn`。

### 11.3 契约（三条不可违反）
- **R1** 同步命令（主线程）禁止：HTTP、起进程、等超时、睡眠、大文件 IO，以及触达会做上述动作的单例。
- **R2** 异步上下文禁止创建/析构阻塞原语（`reqwest::blocking::Client`、任何自带 tokio Runtime 的句柄）；
  必须经 `std::thread` / `spawn_blocking` 边界。首次初始化阻塞单例必须在主线程 `setup` 预热完成。
- **R3** 命令体不承载长任务（加载/转写/下载/合成）；命令只做"投递 + 事件回报"。

### 11.4 审计结果（35 个命令的传递闭包分析）
同步 27 / 异步 8。

**R1 违规（同步命令可达阻塞原语，主线程卡顿风险）：14 个**
`get_gpu_info`、`decode_audio_file`、`rust_unload_sherpa_asr`、`rust_stop_llama_server`、`rust_llama_server_status`、
`rust_get_status`、`rust_unload_asr`、`rust_verify_runtime`、`rust_test_tts_model`、`rust_unload_tts_model`、
`rust_set_tts_clone_voice`、`rust_clear_tts_clone_voice`、`rust_set_tts_language`、`rust_list_tts_speakers`。
（其中 `rust_verify_runtime`/`rust_test_tts_model` 起子进程并轮询最长 6s；`rust_get_status` 启动 800ms + 窗口聚焦
每次都会做 HTTP 健康检查，是最高频路径。）

**R2 危险（async 函数体内直接触达阻塞原语）：2 个**
`rust_load_asr`（已由 10.3.1 的 setup 预热兜住）、`send_to_sidecar_safe`（同类隐患，待修）。

**已合规（经 spawn_blocking 边界）**：`get_vram_status`、`rust_start_llama_server`、`rust_transcribe_llama`、
`download_runtime`、`rust_synthesize`。

### 11.5 整改方案（一次完成）
1. 上述 14 个同步命令 → `async fn` + `spawn_blocking`（业务逻辑、返回值、事件协议均不变）。
2. `send_to_sidecar_safe` 的阻塞调用移入阻塞池（或改由已有预热单例承担）。
3. **护栏**：把本次的传递闭包审计脚本固化为 `scripts/audit-command-context.py`，纳入提交前/CI 检查；
   新增命令若违反 R1/R2 直接失败，杜绝复发。
4. **验收**：用 11.2 的 CDP 探针法逐命令复测——改造后命令运行期间探测 RTT 应保持 ~10ms 量级（基线 7ms）。

### 11.6 影响面与风险
- 前端无需改动：sync/async 命令在 JS 侧都是 `invoke` 返回 Promise。
- 风险中等偏低，但需逐命令验证行为等价（返回时序、事件顺序、错误语义），特别是 `rust_get_status`
  （前端启动对账依赖它的事件）。
- 建议分批：先最痛子集（`rust_stop_llama_server` / `rust_unload_*` / `rust_verify_runtime` / `rust_get_status`），
  再清剩余。

### 11.7 接口契约与 UI 影响（改造前必须锁死）
**结论：UI 获取状态的方式不变，前端几乎零改动；复杂度落在 Rust 侧。**

**(a) 调用方式不变**：sync/async 命令在 JS 侧都是 `invoke()` → Promise。既有调用点（`useStartup` 800ms/聚焦对账、
`modelLoader`、`FrameworkPanel`）无需改动。

**(b) 返回类型：只有带 `State<'_, _>` 借用参数的命令必须改成 `Result`**（tauri 编译期强制），共 6 个：
`rust_test_tts_model`、`rust_unload_tts_model`、`rust_set_tts_clone_voice`、`rust_clear_tts_clone_voice`、
`rust_set_tts_language`、`rust_list_tts_speakers`。其中前 5 个本来就是 `Result`；只有 `rust_list_tts_speakers`
需要从 `serde_json::Value` 改为 `Result<_, String>`，但**成功与业务失败一律 `Ok(...)`**，前端读到的 JSON 形状不变。
其余 9 个（`get_gpu_info`、`rust_llama_server_status`、`rust_get_status`、`rust_verify_runtime`、`decode_audio_file`、
`rust_unload_sherpa_asr`、`rust_stop_llama_server`、`rust_unload_asr`）返回类型保持不变。

**(c) 硬规则：不得把"业务失败"改成 reject**。`FrameworkPanel.tsx:69` 为 `const r = await rustVerifyRuntime(fw)`
（无 try/catch，靠 `r.state` 判别），若改成 `Err` 会变成未捕获 rejection 并破坏该面板。业务失败必须继续 resolve
同形状 JSON，只有协议级异常才 `Err`。

**(d) 唯一需要 UI 配合的点（1-2 行，可选）**：改造后 `rust_get_status` 与聚焦/超时对账可能真并发（现状被主线程
内联串行，天然不重叠），快照事件与响应可能乱序到达，导致陈旧快照覆盖新状态。对策（推荐两者都做）：
1. Rust 侧给 `status_snapshot` 加单调 `seq`；
2. 前端在 `useSidecarEvents.ts` 的 `status_snapshot` 分支加一行守卫（`if (seq < lastSeq) break;`）；
3. 可选加强：Rust 侧"单飞"，并发对账合并为一次。
消费点本身是幂等纠偏（仅当状态不一致才写），故即使不加守卫影响也有限。

**(e) 真正的成本在 Rust 侧**：并发放开后，今天被"主线程串行"掩盖的竞态会显形——状态查询将与模型加载/卸载
真正并行，因此快照必须在**同一把锁内原子读取**（engine 状态 + loaded + model + device 一次取齐），
否则可能出现"半个状态"。此项必须与改造同批完成。

**(f) 收益**：`rust_get_status`（启动 800ms + 每次窗口聚焦）不再占用主线程做健康检查；stop/unload/verify
（最长 6s）期间 UI 完全可交互，不再"未响应"。状态的获取路径（事件 + invoke 返回）两条均保留。
